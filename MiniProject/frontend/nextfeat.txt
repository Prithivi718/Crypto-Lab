# Detailed Prompt — Fix Workflow → Analysis Execution State / Premature Report Fetch

Fix the current SecureNet frontend execution-state and Workflow → Analysis transition bug. **Do not redesign the existing UI, components, styling, or backend services. Modify existing files only where strictly required for this integration/state fix. Preserve all current functionality.**

## Current problem

The application currently mounts `AnalysisPage` inside `MissionPage` at the same time as `PipelinePage`. `MissionPage` stores the Workflow's `executionId` immediately when `/api/workflow/start` succeeds. This causes `AnalysisPage` to see an `executionId` **before any workflow step has executed** and immediately call:

```text
GET /api/report/:executionId
```

The execution context is still in:

```text
status = "running"
```

because `executionStore.createExecution()` initially creates the execution with a running state.

As a result, the Analysis section is displaying:

```text
EXECUTION FAILED
```

while the Pipeline is still sitting at:

```text
01 / 09
Step 01 Operation
```

This is not a real cryptographic failure. It is a frontend lifecycle/state-management problem caused by fetching the final report before Workflow completion.

---

# 1. Fix the Workflow execution lifecycle

Do NOT treat the `executionId` returned by:

```text
POST /api/workflow/start
```

as an Analysis-ready execution.

When Workflow starts, store:

```text
workflowId
workflowExecutionId
```

but do **not** make it available to `AnalysisPage` as the active report execution yet.

Use separate state concepts such as:

```js
workflowId
workflowExecutionId
analysisExecutionId
workflowComplete
processRunData
```

Do not reuse one `executionId` state for every purpose.

---

# 2. Workflow start behavior

Current flow:

```text
RUN SECURE DEMONSTRATION
        ↓
POST /api/workflow/start
        ↓
workflowId + executionId
        ↓
set executionId
        ↓
AnalysisPage immediately fetches report
```

Change to:

```text
RUN SECURE DEMONSTRATION
        ↓
POST /api/workflow/start
        ↓
workflowId + workflowExecutionId
        ↓
show Pipeline
        ↓
DO NOT fetch Analysis yet
```

At this point:

```text
workflowComplete = false
analysisExecutionId = null
```

The Pipeline may use `workflowId` and `workflowExecutionId`, but Analysis must remain in an inactive/empty state.

---

# 3. Analysis must NOT fetch merely because an execution ID exists

`AnalysisPage` currently uses:

```js
useEffect(() => {
    if (!executionId) return;
    getReport(executionId);
}, [executionId]);
```

This behavior is too eager for Workflow mode.

Change the contract so Analysis fetches a report only when it has an **analysis-ready execution ID**.

The logic should conceptually be:

```text
No analysisExecutionId
    ↓
Do not call GET /api/report/:executionId

analysisExecutionId exists
    ↓
GET /api/report/:executionId
```

Do not make Analysis fetch a report simply because Workflow has started.

---

# 4. Process mode must still work immediately

There are two execution modes and they must remain different.

## Workflow

```text
POST /api/workflow/start
        ↓
9 individual workflow steps
        ↓
Step 9 completes
        ↓
analysisExecutionId becomes available
        ↓
Analysis fetch
```

## Process

```text
POST /api/process/run
        ↓
complete algorithm executes in one request
        ↓
executionId returned
        ↓
analysisExecutionId can immediately be set
        ↓
Analysis fetch
```

Do NOT delay Process Analysis unnecessarily because Process is already complete when its API response returns.

# 5. Step execution must be authoritative

Do not use:

```text
currentStep === 9
```

alone to determine Workflow completion.

The source of truth must be the actual Step 9 API response.

After calling:

```text
POST /api/workflow/step
```

for Step 9:

1. Wait for the Promise to resolve.
2. Check the actual response.
3. Confirm:

   ```js
   response.step === 9
   ```
4. Confirm:

   ```js
   response.status === "completed"
   ```
5. Confirm the response belongs to the expected `workflowId`.
6. Only then set:

   ```text
   workflowComplete = true
   analysisExecutionId = response.executionId
   ```

Do not set completion before the response arrives.

Do not infer completion from local UI state.

Do not use a stale `activeExecId`.

Do not use the execution ID from workflow initialization if Step 9 has not completed.

# 9. Do not accidentally overwrite Process execution

Process has its own execution.

When:



set:


and store:


Then Analysis is allowed to fetch the report.

Do not let a later Workflow state update overwrite the Process execution ID.

# 10. Separate Workflow and Process state

Use explicit state semantics.

Recommended:

```js

const [workflowExecutionId, setWorkflowExecutionId] = useState(null);

const [analysisExecutionId, setAnalysisExecutionId] = useState(null);

```

Meaning:

```text

→ whether Step 9 has actually completed

analysisExecutionId
→ execution that Analysis is allowed to inspect

processRunData
→ direct Process API result
```

Do not collapse these meanings into one state variable.

# 13. Distinguish fetch failure from execution failure

A failed:

```text
GET /api/report/:executionId
```

may mean:

* network error
* backend unavailable
* execution not committed yet
* malformed response
* execution ID not found
* actual execution failure

Do not convert every one of those into:

```text
EXECUTION FAILED
```

Use separate UI states.

For example:

```text
REPORT FETCH FAILED
```

for transport/API problems.

Use:

```text
EXECUTION FAILED
```

only when the backend explicitly reports an execution failure.

---

# 14. Prevent race conditions with report fetching

The Analysis fetch should happen only after the correct execution is ready.

When `analysisExecutionId` changes:

```text
old report state
↓
clear stale report
↓
set loading = true
↓
fetch current execution report
↓
validate response belongs to current executionId
↓
set report
↓
loading = false
```

Prevent an older asynchronous request from overwriting a newer execution's report.

Use a mounted/abort/stale-request guard as appropriate.

---

# 15. Report status must not default to failure

Do not make any of these assumptions:

```text
null report = failed
loading = failed
missing report = failed
fetch error = failed
```

Instead:

```text
null + loading
→ LOADING

null + no execution
→ WAITING

null + fetch error
→ REPORT FETCH ERROR

report.summary.status === "failed"
→ EXECUTION FAILED

report.summary.status === "completed"
→ COMPLETED
```
