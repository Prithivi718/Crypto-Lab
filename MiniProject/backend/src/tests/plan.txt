1. The architecture I recommend

Think of the four services like this:

                    CRYPTO SERVICE
                         │
              actual cryptographic work
                         │
        ┌────────────────┴────────────────┐
        │                                 │
        ▼                                 ▼
 WORKFLOW SERVICE                   PROCESS SERVICE
 deep demonstration                complete execution
 step-by-step                       encryption + decryption
        │                                 │
        └──────────────┬──────────────────┘
                       │
                 EXECUTION DATA
                       │
                       ▼
                 BENCHMARK SERVICE
              analyze collected metrics
                       │
                       ▼
                  REPORT SERVICE
             build final analysis/report
                       │
                       ▼
                 OUTPUT / ANALYSIS

And the roles become extremely simple:

crypto.service.js

How to perform cryptography

workflow.service.js

How to demonstrate cryptography step by step

process.service.js

How to run the whole cryptographic operation in one shot

benchmark.service.js

How to analyze execution measurements

report.service.js

How to turn everything into the final human-readable report

That is the separation I'd stick with.

2. One important change to your idea

You said:

benchmark should be analyzing those metrics at each step or at complete algorithm, from a single function call.

Yes.

But I would not call benchmark.service.js from every crypto function.

Instead, introduce one small lower-level timing/measurement mechanism.

You already have:

measureAsync()
measureSync()

in timingUtils.js, and your benchmark service is currently using them around every crypto operation.

Use those as the measurement layer.

Then:

timingUtils
    ↓
collects raw timings
    ↓
execution context
    ↓
benchmark.service
    ↓
analyzes them

So:

Timing utility = stopwatch
Benchmark service = analyst

That's much cleaner than making Benchmark the stopwatch.

3. Introduce an executionContext

This is the missing piece.

When either Workflow or Process begins, create an execution context.

For example:

{
    executionId: "exec-123",

    input: {
        message: "...",
        filename: "mission.txt",
        size: 284
    },

    steps: [],

    metrics: {
        times: {},
        sizes: {},
        status: {}
    },

    cryptographicData: {
        ed25519: {},
        ecdh: {},
        hkdf: {},
        rsa: {},
        aes: {},
        signature: {}
    }
}

This object becomes the single source of truth for that execution.

4. What gets stored in this execution context

This is where your confidential values go.

For your demo, the execution context can contain:

INPUT
├── plaintext
├── filename
└── file size

ED25519
├── public key
└── private key

ECDH
├── Base A public key
├── Base B public key
└── shared secret

HKDF
├── shared secret
├── salt
├── info
└── session key

RSA
├── public key
├── private key
└── wrapped session key

AES
├── plaintext
├── session key
├── ciphertext
├── IV
└── auth tag

SIGNATURE
└── signature

DECRYPTION
├── recovered session key
└── recovered plaintext

VERIFICATION
├── signature valid
├── shared secret match
├── decryption success
└── plaintext match

TIMING
├── Ed25519 generation
├── ECDH
├── HKDF
├── RSA generation
├── RSA wrap
├── AES encrypt
├── signature
├── signature verify
├── RSA unwrap
├── AES decrypt
└── total

Now Workflow and Process don't need separate data models.

They can both contribute to the same execution structure.

5. Your masking requirement should become one utility

Yes — absolutely put this in utils.

Something like:

utils/
└── maskSensitive.js

The utility should support:

maskSensitive(value)

Example:

Actual:
fd44dd021993e0bb39097461

Displayed:
fd44********

Or, for a longer value:

Actual:
5a7e9c42c1d84f8a...

Displayed:
5a7e********

I would make the function configurable:

maskSensitive(value, {
    visible: 4,
    maxVisibleLength: 10,
    maskChar: "*"
})

But the important rule is:

first 4 characters
+
masked remainder

For example:

PRIVATE KEY
7f91********

PUBLIC KEY
a81c********

SHARED SECRET
9e42********

SESSION KEY
31fd********

For your report, keep both:

{
    raw: actualValue,
    display: maskedValue
}

That is powerful because:

backend retains actual value for report generation
UI can show masked version
exported report can choose what to display
you don't repeatedly write masking logic everywhere

15. What happens to the REAL keys?

This is the important distinction:

API step response

Masked.

Execution context

Full values.

Report service

Has access to full values.

Frontend display

Can choose masked/full depending on what you're designing.

That gives you the flexibility you want.

For example:

API:
sessionKey = "bc72********"

Internal:
sessionKey = "bc72a8f1cc98...."

Report:
sessionKey = "bc72a8f1cc98...."

Since this is a cryptography demonstration rather than a real production secure channel, that's reasonable for your project. But these should be demo-generated keys only, never real operational secrets.

20. The most important part: Report should NOT rerun the algorithm

This answers your biggest question.

You asked:

report.service.js can use the same benchmark.service.js again to gain those input, process, and output or can track and store responses when workflow/process is runned.

Choose the second approach.

Store/collect during execution.

Do NOT rerun crypto during report generation.

So:

Workflow/Process executes
        ↓
captures data
        ↓
stores execution context
        ↓
Analysis page requests report
        ↓
Report service reads stored execution
        ↓
Benchmark service analyzes stored timings
        ↓
Report assembled

That means the report describes the actual execution that just occurred.

Not a second execution.

That's a major difference.

26. One small correction to your wording

You called Benchmark the “parent of time tracking.”

I'd reverse that.

Use:

timingUtils
     ↓
TIME TRACKING
     ↓

     ↓
benchmark.service
     ↓

Because measureSync() and measureAsync() are infrastructure-level utilities. Your current benchmark service already demonstrates this pattern by wrapping operations with them.
